# 구조와 설계 원칙

현재 실행형 v0.1.0의 사용법과 API는 README 및 TOOL-CONTRACTS.ko.md를 따른다. 아래 목표 구조에는 향후 항목이 포함된다. 현재 구현은 src/evidence_harness, SQLite 원장, runner, CLI, setup 및 테스트이며 events.jsonl 자동 내보내기와 메모리 샘플러는 포함하지 않는다.

## 1. 목적과 범위

미지의 개발 과제에서 재사용할 부분은 완성 앱보다 **판단과 검증의 절차**입니다. 이 하네스는 도메인 답안을 제공하지 않고, 실제 작업 중 생긴 근거를 정리합니다.

하네스와 AI의 역할을 구분합니다.

- AI 호스트: 자료 해석, 계획 제안, 코드 작성, 디버깅, 검토.
- MCP: 명시적인 도구 호출, 로컬 기록 저장, 등록된 검사 실행, 조건이 맞는 결과 비교.
- 참가자: 요구 해석 확인, 우선순위 결정, 결과 검토, AI 제안을 믿은 이유에 대한 본인의 판단.

다중 에이전트 자동 토론, 외부 모델 라우팅, 자율 웹 수집은 최소 버전에 포함하지 않습니다. 같은 AI의 역할 변경을 독립 검증으로 부르지 않습니다.

## 2. 공개 소스와 실행 데이터를 분리

다음은 **향후 구현할 목표 구조**이며 현재 존재하는 실행 코드 목록이 아닙니다.

```text
public-harness/
  src/evidence_harness/
    server.py             # MCP 도구 어댑터
    core.py               # MCP 없이도 호출할 수 있는 핵심 로직
    ledger.py             # 이벤트/관계/조회
    runner.py             # manifest 기반 제한 실행
    compare.py            # 비교 적격성·통계
    cli.py                # 같은 core를 쓰는 로컬 CLI
  schemas/
  templates/
  examples/               # 합성 데이터만
  tests/
  pyproject.toml
  uv.lock                 # 구현 시 실제 해석한 의존성 고정
  README.md
  LICENSE

provided-workspace/
  application/            # 실제 제출할 앱
  checks/                 # 실제 과제의 검사·수동 정답·fixture
  harness.workspace.json  # 실제 작업 경로와 허용 검사
  evidence-private/
    ledger.sqlite3        # 트랜잭션과 request_id 고유성
    events.jsonl          # DB에서 생성하는 읽기용 내보내기
    runs/<run_id>/
      receipt.json
      stdout.log
      stderr.log
      raw-metrics.json
      snapshots/          # 실제 코드·검사·fixture·lockfile 보존
    review/
```

공개 저장소 밖에 실행 데이터를 둡니다. `.gitignore`는 실수 방지용 보조 수단이며 외부 공개를 막는 보장은 아닙니다. 과제 지문, 제공 데이터, 개인 접속 정보, 실제 코드와 결과를 공개 예제로 복사하지 않습니다. 자동 push·업로드·텔레메트리는 구현하지 않습니다.

## 3. 모듈 선택

제안 스택은 Python 3.11 이상 + 호환 MCP SDK + SQLite입니다. 이유는 작은 프로세스 하나로 기록과 실행 도구를 만들기 쉽고, SQLite로 기록의 중복과 부분 저장을 다루기 좋기 때문입니다. 실제 제공 환경에서 Python/SDK 호환성을 먼저 확인해야 하며, 미리 호스트 업데이트를 요구하지 않습니다.

하네스 언어와 제출 앱 언어는 별개입니다. 앱 스택은 제공된 저장소·평가 기준·팀 또는 본인의 숙련도·구현 시간에 맞춥니다. 기존 스택이 있으면 이를 우선 검토합니다. 빈 웹 과제라면 TypeScript와 단일 앱 서버, 관계형 저장이 필요하면 SQLite를 후보로 삼을 수 있지만 자동 정답으로 고정하지 않습니다.

## 4. 기록의 세 층

| 층 | 기록할 내용 | 증거로 해석할 범위 |
|---|---|---|
| AI 제안 | 예상 복잡도, 방법 제안, 코드 설명 | 아직 검증되지 않은 주장 |
| 선택 | 후보, 선택 이유, 제외한 이유, 비용·한계 | 후보자 또는 AI가 보고한 판단 |
| 관찰 | 실제 명령, 종료 상태, 정답 검사, 원시 측정 | 해당 코드·입력·환경에서 확인한 결과 |

AI 제안에 대해 `accepted`를 기록했다고 해서 `verified`가 되지 않습니다. 구조 검사 통과, 프로세스 종료코드 0, 정답 검사 통과, 성능 우위, 사용자 흐름 검증은 서로 다른 상태입니다.

요구사항과 근거의 연결은 다음과 같습니다.

```text
REQ ──implemented_by──> 코드 스냅샷
 │
 └──checked_by───────> CHK ──executed_as──> RUN

DEC ──motivated_by───> REQ
 └──supported_by─────> RUN / 공식 문서 / 명시적 추론

AI  ──assessed_using─> RUN / 반례 / 공식 문서
```

직접 관찰하지 않은 사용자 행동·생각을 기록하지 않습니다. `reported_by`가 `codex`인 판단을 후보자 본인의 발언으로 바꾸지 않습니다. 과거 사건 수정은 원본을 덮어쓰지 않고 새 이벤트의 `supersedes_id`로 남깁니다. 단, 로컬 append-only 기록은 변조 방지 시스템을 뜻하지 않습니다.

## 5. 실행과 변경 감지

등록된 `check_id`만 실행하고 도구 인자로 자유 셸 문자열을 받지 않습니다. 검사는 `argv` 배열, 작업 디렉터리, 대상 경로, fixture, oracle, 제한 시간, 반복 수로 선언합니다. manifest는 작업공간 안에서 검토하고 등록하며, 실행 직전 해시를 다시 확인합니다.

실행 전 실제 소스·검사·입력·의존성 파일을 스냅샷에 저장하고 SHA-256을 기록합니다. 실행 중 대상 파일이 바뀌면 `contaminated`, 실행 후 현재 작업 코드와 달라지면 `stale`로 계산합니다. 내용 해시만 보관하고 입력·소스를 버린 결과를 완전 재현 가능하다고 표시하지 않습니다.

프로세스는 `shell=False`, 시간 제한, 동시 실행 1개, 원시 로그 크기 제한과 종료 시 자식 프로세스 정리를 사용하도록 구현합니다. stdout에 MCP 통신 이외의 로그를 쓰지 않습니다. 이것은 보안 샌드박스가 아닙니다. 등록한 코드 자체가 네트워크·파일·하위 프로세스를 사용할 수 있으므로 제공 환경의 실제 제한을 따릅니다.

반복 측정이 MCP 도구의 응답 제한을 넘지 않도록 `run_check`는 로컬 작업을 시작하고 `job_id`를 즉시 반환하는 비동기 방식으로 설계합니다. `evidence_status`로 진행·완료·실패를 확인하고, 최종 receipt가 저장된 run만 비교합니다. 임의의 대기나 재호출로 중복 실행하지 않습니다.

## 6. 비교 기준

먼저 정답·제약을 확인하고, 통과한 결과끼리 개선을 비교합니다. 조건이 다르면 자동 우열 판정을 거절하고 차이만 보여줍니다.

- 같은 입력 내용·입력 크기·seed·정답 기준·테스트 버전·환경·의존성 조건을 비교합니다.
- baseline과 candidate는 별도 소스로 보존하고, 같은 비교용 검사로 실행합니다.
- 동일 프로세스 안의 함수 시간과 새 프로세스의 전체 실행 시간을 섞지 않습니다.
- 초기화·로딩·캐시 상태·워밍업·측정 순서(예: A-B-B-A)를 기록합니다.
- 기본 제안은 워밍업 1회, 측정 5회이며 시간에 맞게 조정합니다. 작은 n에서 p95/p99를 확정적으로 해석하지 않고 중앙값·최소·최대와 원시 samples를 표시합니다.
- 입력이 작은 경우 수동 정답이나 완전 탐색과 비교합니다. 큰 입력은 별도 제약 검사와 다양한 분포를 사용합니다.
- 제약 위반이 있는 빠른 결과는 우수한 결과로 선정하지 않습니다.
- 품질, 알고리즘 지연, API/DB 지연, 화면 전체 반응, 메모리는 별도 지표입니다.
- 최적해 또는 유효한 하한이 없으면 '최적'이라고 하지 않습니다. 관측된 개선이라고 표현합니다.

시간 예산상 정확성만 확인했다면 성능 항목은 `not_measured`로 남깁니다. 실행 실패와 미실행을 혼동하지 않습니다.

## 7. 도메인별 교체 지점

| 과제 유형 | 그대로 쓰는 부분 | 새로 작성할 검사 |
|---|---|---|
| 배정·스케줄링 | 요구/판단/실행/비교 기록 | 제약 위반, 목적함수, 작은 입력의 정답 |
| 데이터 분석 | 동일 기록 모델 | 누락·중복·분할 누수·산식·재현성 |
| 업무 웹 서비스 | 동일 기록 모델 | 핵심 사용자 흐름, 저장, 권한, 오류 |
| 검색·추천 | 동일 기록 모델 | 평가 집합, 지표 정의, 품질·지연 분리 |

특정 과제의 해법이나 전체 앱은 공개 하네스에 미리 넣지 않습니다.

## 8. 후속 설명을 위한 작업 습관

큰 결정을 내릴 때마다 '왜 / 대안 / 확인한 사실 / 못 확인한 사실' 네 가지를 짧게 남깁니다. AI가 코드 블록을 제시하면 이름이나 설명만 믿지 말고 실제 실행·작은 정답·반례를 확인합니다.

과제 수행 단계에서 후보자 본인이 다음을 설명해 봅니다.

1. 핵심 입력과 출력, 반드시 지키는 제약.
2. 선택한 방법의 작동 순서와 대안의 비용.
3. 실제 비교한 조건과 지표, 반례.
4. AI 제안을 채택·수정·거절한 구체적인 이유.
5. 현재 구현의 한계와 시간이 더 있다면 확인할 점.

이 점검은 답안 암기나 예상 문항의 자동 답변 생성이 아닙니다. AI가 금지되는 평가 단계에서는 AI와 MCP 사용을 중단하고, 기록 열람 허용도 임의로 가정하지 않습니다.
